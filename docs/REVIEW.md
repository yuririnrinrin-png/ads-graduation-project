# レビュー結果（UI/UX・エンジニア）

Phase 0（要件確定・UIモック作成）が終わった段階で、UI/UXデザイナー役とプロのエンジニア役の2つのサブエージェントに設計とモックをレビューさせた結果の記録です。まだ `REQUIREMENTS.md` / `DESIGN.md` 本体には反映していません。Phase 1 に着手する前に、ここで洗い出した項目を先に決めておくことを推奨します。

## 全体の結論

デザイン面は「うまくいった時」の見た目はできているが、「失敗した時・入力ミス時」の設計が抜けている。技術面は要件・設計自体はしっかりしているが、実装前に3つの土台（メタデータの保存先・処理の制御方式・人物の顔を固定する方法）を先に決めないと、Phase 1 の作り直しリスクが大きい。

## A. UI/UXレビュー

対象: `docs/mockups/product-ui.html` および要件・設計ドキュメント。

### 良い点

- レビュー画面の役割ベースのグルーピング（Detail / Wear / Body & Inset）が要件の10枚の型とそのまま対応していて分かりやすい
- メイン写真であることをサムネイル上のバッジで直接表示している（視線移動が少ない）
- 進捗画面がプログレスバーとステージ一覧の両方で状態を見せている
- ブランドの配色・フォントの組み合わせに一貫性があり、高級感が出ている
- インセット元の選び直しが、結果と同じ場所（レビュー画面）に置かれている

### 改善提案（重要度：高→低）

1. **失敗時のUIが一切設計されていない** — 進捗・レビュー画面ともに失敗状態の見た目がない。段階名つきの失敗表示＋リトライボタンを追加する
2. **「再生成」がテキストリンクのみで発見しにくい・誤操作しやすい** — ボタン形状にし、実行前に軽い確認を出す
3. **メイン写真の変更方法が示されていない** — 2・3枚目をメインに切り替える導線を追加する
4. **新規ジョブ画面に入力順序・完了状態のガイドがない** — 未選択項目がある場合は生成ボタンをdisabledにし、フィードバックを出す
5. **カテゴリ変更時、着用シーンの部位対応がその場で分からない** — 「着用シーンでは腕まわりを撮影します」等のヒントを添える
6. **全身トーン「2つ選ぶ」の制約に対するフィードバックがない** — 「2/2 選択中」の表示、上限到達時は他をdisabled風に
7. **着用シーン間の色・トーン比較がしづらい** — カラースウォッチの常時表示、または拡大比較モーダル
8. **進捗画面が単調で、2〜4分の離脱防止策がない** — ディテール完成分の先出し表示、離脱許可メッセージ
9. **小さい文字・低コントラストな箇所が多い** — 必須テキストは12px以上・コントラスト比4.5:1以上を目安に見直す
10. **フォームのアクセシビリティ対応が設計書に明記されていない** — `label for`とinput idの対応、aria-required等をDESIGN.mdに一言明記する

### 検討に値する追加アイデア

- 14日削除のカウントダウン表示（ダウンロード忘れ防止）
- アップロード直後の簡易バリデーション（撮影条件を満たさない写真を事前に警告）
- 複数枠の一括再生成・一括OK操作

## B. エンジニアレビュー

対象: `README.md` / `docs/REQUIREMENTS.md` / `docs/DESIGN.md` / UIモック。

### 良い点

- 失敗時のリトライ設計が最初から段階名つきで定義されている（`REQUIREMENTS.md` 7章）
- 枠再生成のルールが「どの段階を再実行するか」まで表になっている（`DESIGN.md` 枠再生成表）— 画像生成APIの呼び出しを避ける良い設計思想
- v1でやらないことの線引きが明確
- 未決事項を先に見える化している

### リスク・改善提案（重要度：高→低）

1. **ジョブのメタデータを永続化するデータベースが構成図にない** — Redisはキュー用途で、ジョブ履歴の検索・一覧には向かない。PostgresなどのRDBを正式なコンポーネントとして構成図に追加し、「正のデータ源」とする
2. **パイプラインが分岐・合流する構造なのに、制御方式が未確定** — Cutout→Detail/Scene→Composite という分岐・合流（DAG）構造を、複数の小さなキュージョブに分けると複雑になりやすい。「1ジョブ＝1プロセスが7段階を順に実行し、各段の結果をチェックポイントとして残す」方式を推奨
3. **人物の「同一persona維持」の技術的実現方法がまだ仮説段階** — 単純なseed固定だけでは、プロンプトが変わると顔も変わりやすい。参照画像で顔を固定する専用技術（IP-Adapter FaceID、PuLID、InstantID等）がfal.aiで使えるか、早めに小さく検証する
4. **リング・ネックレスの3D的なズレ（パース）に対する自動調整手段がない** — 回転角の推定・調整をtransform JSONに持たせる、または「品質のばらつきは人手レビューで救う」前提を関係者と事前合意する
5. **Composite単独再実行に必要な中間データ（人物のみのシーン画像）の保存先が未定義** — これがないと位置調整のたびにSceneGenをやり直すことになり、「単枠再生成は数十秒〜1分」を満たせない
6. **進捗表示の実装方式（ポーリング/SSE/WebSocket）が未確定** — まずは3〜5秒間隔のポーリングで十分
7. **画像生成APIのコストに歯止め（上限）がない** — ジョブ単位でAPI呼び出し回数に上限を設け、月次のコストを可視化する
8. **認証・APIキー管理・アップロード画像の取り扱いの具体策が不足** — APIキーはワーカー側の環境変数のみに置く、アップロードのサイズ・形式チェックを明文化する
9. **監視・ログ・テスト戦略が設計に存在しない** — ログはジョブID・段階名・処理時間を必ず出す形に統一。座標処理はユニットテスト、外部API呼び出しはモックに置き換える
10. **ワーカーのスケール・同時実行数の想定がない** — 想定同時ジョブ数を決め、それに合わせてワーカー並列数・GPU有無を検証する

### Phase 1 着手前に追加で決めておくべき技術的決定事項

1. Job/JobAsset等メタデータ用DBの選定とスキーマ（Postgres + Prisma等）
2. パイプラインのオーケストレーション方式（1ジョブ1プロセス＋チェックポイント／複数RQジョブ連携）
3. persona一貫性の実現方向のスパイク検証（参照画像を条件に使う専用モデルの実用性）
4. Composite単独再実行に必要な中間データの持ち方
5. 進捗通知のAPI形（ポーリング前提かSSE前提か）

`REQUIREMENTS.md` の未決事項の優先順序は、記載順（①画像生成API/切り抜きモデルの最終ベンダーとコスト → ②プリセットの実デザイン → ③本番ホスティング構成 → ④AI表記の要否）が妥当。①は上記リスク3・7の検証と直結し他の決定の前提になるため最優先、④はエンジニアリングをブロックしないため一番後で良い。
